# Architecture

How PSGnuUtils is put together and why. Read this before changing anything in `src/PSGnuUtils/Private/Core`.

## Goals

1. **GNU compatible**: same option syntax (`-rn`, `--lines=5`, `--li 5`, `--`), same output format, same messages
   (`head: cannot open 'x' for reading: No such file or directory`) and exit codes.
2. **Opt-in**: importing the module changes nothing. GNU names are enabled per util (`Enable-GnuUtil`).
3. **Portable**: Windows PowerShell 5.1 and PowerShell 7+ on Windows, Linux and macOS, with one code base and no
   compiled code.
4. **PowerShell friendly**: utils are pipeline citizens (pipeline input = stdin, output = string lines, errors go to
   the error stream).

## Layout

```
src/PSGnuUtils/
  PSGnuUtils.psd1          manifest (FunctionsToExport generated by ./build.ps1 -Manifest)
  PSGnuUtils.psm1          loader: Private -> Utils -> Public, exports, import configuration
  Private/Core/            framework (every util uses this)
    Registry.ps1           util specs, option normalization, name resolution
    Arguments.ps1          getopt_long compatible parser
    Context.ps1            Initialize-GnuUtil / Complete-GnuUtil, option accessors, errors, exit codes
    Input.ps1              pipeline input as stdin, file reading, wildcard expansion
    Output.ps1             line and NUL-record output helpers
    Help.ps1               --help text generated from the spec
    Path.ps1               path resolution, basename/dirname logic, symlink resolution
    Platform.ps1           OS detection (PS 5.1 has no $IsWindows), uname data, Unix modes
    Aliases.ps1            Enable/Disable of GNU name aliases, restoring replaced aliases
    Configuration.ps1      Import-Module -ArgumentList handling
  Private/Lib/             code shared by several utils (checksums, base encodings, sizes, escapes, number formatting, head/tail)
  Public/                  Get-GnuUtil, Enable-GnuUtil, Disable-GnuUtil
  Utils/<name>.ps1         one file per util: Register-GnuUtil spec + Invoke-Gnu<Name> function (+ private helpers)
tests/
  TestHelpers.ps1          Invoke-TestGnu, New-TestFile, platform helpers
  Module.Tests.ps1         meta tests (exports, help, docs, option coverage, ASCII)
  Core/ Public/ Utils/     unit tests; one Utils/<name>.Tests.ps1 per util
```

## Naming

* Every util is a normal PowerShell function `Invoke-Gnu<Name>` (`Invoke-GnuHead`, `Invoke-GnuSha256sum`). The
  function is always exported and can always be called by that name.
* The GNU name (`head`) is an **alias** created by `Enable-GnuUtil`. Aliases have the highest command precedence
  (alias > function > cmdlet > native executable), so an enabled GNU name wins over `cat -> Get-Content`, the
  `mkdir` function, `sort.exe` and `/usr/bin/head` alike.
* The manifest exports no aliases. Aliases are created at runtime only for the utils the user asked for.

## Enabling utils (Aliases.ps1)

* `Enable-GnuUtil` creates `Set-Alias -Scope Global -Option AllScope -Description PSGnuUtils <name> Invoke-Gnu<Name>`.
* If a global alias with that name exists (e.g. `cat`), its definition, options and description are saved in
  `$script:GnuEnabledUtils[name]` and restored by `Disable-GnuUtil` or `Remove-Module` (`OnRemove` handler).
* Our aliases are always `AllScope` because Windows PowerShell's built-in aliases are `AllScope` and that flag
  cannot be removed from an existing alias. `Remove-Item Alias:\x` from inside the module reliably removes an
  `AllScope` alias from the global scope (verified on 5.1 and 7.6), after which the original is re-created with its
  original options.
* `-NoClobber` skips names that already resolve to any command.
* Configuration: `Enable-GnuUtil` in the profile, or `Import-Module PSGnuUtils -ArgumentList @{ All = $true; Exclude = 'ls' }`
  (keys `All`, `Name`, `Exclude`, `NoClobber`).

## Why utils are simple functions reading `$args`

PowerShell parameter binding cannot express GNU command lines:

* parameter names are case-insensitive (`-n` vs `-N`, `-r` vs `-R`);
* bundled flags (`-rn`) cannot be split;
* advanced functions get common parameters, so `-v` becomes `-Verbose`, and `-e` / `-o` are ambiguous.

So util functions have **no `param()` block and no `[CmdletBinding()]`**. They pass the raw `$args` to
`Initialize-GnuUtil`, which runs the getopt_long compatible parser in `Arguments.ps1`.

Facts about `$args` (verified on 5.1 and 7.6, see DEVLOG 2026-11-07):

* `-5` arrives as `[int]`, `1.5` as `[double]`, `a,b` as an array: `ConvertTo-GnuArgumentList` flattens and converts
  with invariant culture.
* A literal `--` and quoted `'--'` both reach the function.
* `-n:5` arrives as two arguments, `'-n:'` and `5` (PowerShell syntax); this is not supported.

## The util spec

`Register-GnuUtil @{ ... }` keys (defaults in `Registry.ps1`):

| Key | Meaning |
|---|---|
| `Name`, `Category`, `Synopsis`, `Usage` (required) | Identity and `--help` usage lines. |
| `Description`, `Notes` | Extra `--help` text. |
| `Options` | Option definitions: `Short`, `Long`, `Key`, `Arg`, `OptionalArg`, `Multi`, `Value`, `Sets`, `Hidden`, `Help`. |
| `RawArguments` | Do not parse options (echo, true, false); only a sole `--help` / `--version` is special. |
| `StopAtFirstOperand` | POSIX style: options end at the first operand (yes). |
| `FileOperands` | Operands are files: expand wildcards like a Unix shell. |
| `NumericOption` | Short option that `-NUM` maps to (`head -5` = `head -n 5`). |
| `NegativeNumberOperands` | `-5` / `-.5` are operands (seq). |
| `UsageExitCode` | Exit code for usage errors (1; grep will use 2). |
| `OpenErrorFormat`, `ReadErrorFormat` | Util specific wording of file errors (`{0}` name, `{1}` reason). |

Parsed options are stored by `Key`: flags store a count, `Value` options store the constant, `Arg` options store the
last value (or a list with `Multi`). Several options may share a `Key` (e.g. head's `-c` and `-n` share `count` and
set `unit` via `Sets`), which gives GNU's "last one wins" behaviour.

## Util function shape

```powershell
function Invoke-GnuExample {
    <# comment-based help: .SYNOPSIS "GNU example: ...", .DESCRIPTION, .EXAMPLE #>
    begin   { $ctx = Initialize-GnuUtil -Name 'example' -Arguments $args -ExpectingInput $MyInvocation.ExpectingInput }
    process { if (-not $ctx.Done) { Add-GnuPipelineInput -Context $ctx -InputObject $_ } }
    end {
        if (-not $ctx.Done) { <# work: read inputs, emit lines, Write-GnuError on problems #> }
        Complete-GnuUtil -Context $ctx      # emits --help/--version text, sets $LASTEXITCODE
    }
}
```

* `$ctx.Done` is `$true` after `--help`, `--version` or a usage error; the util must not do any work then.
* Utils that can work line by line (cat, head, tee) check `Test-GnuStdinOnly` and process pipeline items in
  `process` instead of buffering them.
* Larger utils keep the function short and move the work into a private helper in the same file
  (`Invoke-GnuWordCount`, `Invoke-GnuSequence`). Helpers used by more than one util live in `Private/Lib`.

## Input model (Input.ps1)

* **Pipeline input is stdin.** Strings are split into lines (`\r?\n`), value types (numbers, booleans) are converted
  with invariant culture, `FileInfo`/`DirectoryInfo` become their full path, and any other object is rendered like the
  console shows it (`Out-String -Stream`, objects buffered so a table has one header, blank padding lines trimmed).
  That makes `Get-Process | grep pwsh` work on the visible text.
* Without pipeline input, `-` (or no operand) reads `[Console]::In` (like GNU reading the terminal).
* stdin can be read once; a second `-` reads nothing (like GNU at EOF).
* **Files** are read as UTF-8 (a BOM selects UTF-16/32). Byte oriented utils read raw bytes; pipeline text becomes
  UTF-8 bytes with a LF after every line (so `'hello' | sha256sum` equals `echo hello | sha256sum` on Linux).
* Relative paths resolve against the **PowerShell location** (`$PWD`), never `[Environment]::CurrentDirectory`.
* **Wildcards**: PowerShell does not glob arguments of functions, so `FileOperands` utils expand them like bash:
  existing literal names win (`file[1].txt`), patterns without matches stay literal, dot files only match patterns
  starting with `.`, results are sorted ordinally and keep the directory part as typed.

## Output model (Output.ps1)

* One string per output line, written to the pipeline. Whether the last line had a newline cannot be represented.
* NUL terminated output (`-z`, `-0`, `--null`) is a single string with a NUL after every record.
* Files written by utils (tee) are UTF-8 without BOM with LF line endings.

## Errors and exit codes

* `Write-GnuError` writes `util: message` with `Write-Error`, so `2>$null`, `2>&1`, `$ErrorActionPreference` and
  `-ErrorAction` on callers work as PowerShell users expect. (PowerShell prefixes the displayed message with the helper
  name; the message itself is GNU's.)
* `Write-GnuUsageError` adds `Try 'util --help' for more information.` and uses the spec's `UsageExitCode`.
* Warnings (`md5sum -c` summaries) use `Write-Warning`.
* `Complete-GnuUtil` sets `$global:LASTEXITCODE`, like a native command. Functions cannot set `$?` to `$false`
  without writing an error, so scripts should test `$LASTEXITCODE` (documented for true/false).

## Stopping upstream (known limitation)

GNU `yes | head -n 1` ends because head exits and yes gets SIGPIPE. A PowerShell *function* cannot stop the commands
that feed it: only compiled cmdlets such as `Select-Object -First` can throw the internal
`StopUpstreamCommandsException`. Probes on 5.1 and 7.6 (DEVLOG 2026-11-07) showed that creating a steppable
`Select-Object -First` inside a function terminates the *whole* script instead of just the upstream commands. So:

* head stops *emitting* after N lines but keeps consuming its input;
* with endless producers use `Select-Object -First N` (documented in the help of yes and head).

Ideas for later: a tiny C# cmdlet compiled with `Add-Type` that head pipes into (would need to work on 5.1 and 7).

## Strict mode and compatibility rules

* The module runs under `Set-StrictMode -Version Latest`. In that mode reading a **missing hashtable key with dot
  notation throws** and `.Count` on `$null` or a scalar throws. Therefore specs, option definitions and contexts are
  normalized so every key exists, options are read with `Test-GnuOption` / `Get-GnuOptionValue`, and counts use
  `@($x).Count`. Note `@($null).Count` is 1, so never wrap a variable that may hold `$null`.
* No PowerShell 7-only syntax: no `? :`, `??`, `?.`, `&&`, `||`, `-Parallel`, `clean {}` blocks, `Join-String`.
  PSScriptAnalyzer's `PSUseCompatibleSyntax` (5.1 + 7.0) enforces this.
* No `$IsWindows` / `$IsLinux`: use `Test-GnuWindows` / `Get-GnuPlatform`.
* Use .NET for file I/O (`[System.IO.File]`), not `Get-Content -AsByteStream` (7 only) / `-Encoding Byte` (5.1 only).
* Source and test files are **ASCII only**: Windows PowerShell 5.1 reads BOM-less files as ANSI. Build non-ASCII
  strings with `[char]0xE9`. The built module is written with a UTF-8 BOM anyway. A meta test enforces this.
* Number parsing and formatting use `[System.Globalization.CultureInfo]::InvariantCulture` (the developer machine
  runs a German locale).
* **String comparisons on content must be ordinal.** .NET's culture-aware comparisons treat control characters
  (NUL, U+0080, ...) as ignorable: `"a`0b".EndsWith("`0")` and `"\u0080".EndsWith("`n")` are `$true`, and PowerShell's
  `-eq` is culture-aware too (`[char]0x80 -eq ''` is `$true`). Always pass `[System.StringComparison]::Ordinal` to
  `StartsWith` / `EndsWith` / `IndexOf(string)`, and test emptiness with `[string]::IsNullOrEmpty()`, never `-eq ''`.
  (Found by the first test run, 2026-11-07.)

## Build

`./build.ps1 -Build` writes `out/PSGnuUtils/` with the manifest and a single merged `PSGnuUtils.psm1` (the
`#region Loader` block is replaced by all source files in load order), which loads much faster than dot-sourcing
dozens of files. `-Task TestBuild` runs the full test suite against that output; CI does both.
